# Initial candidate registry

These are research candidates, not enabled setting mutations. No candidate may run until its client-OS support, adapter capability, authorization, durable rollback, and independent failure recovery have been verified. Original values must be read and restored exactly; factory reset is not rollback.

| Identifier | Mechanism and hypothesis | Support/privilege gate | Risks / restart | Verification / rollback |
| --- | --- | --- | --- | --- |
| `tcp.receiveAutoTuning` | Receive-window sizing can constrain bandwidth-delay utilization | Supported Windows client TCP settings; service-only write | Throughput regression; preserve modern defaults | Read supported TCP setting, compare repeated throughput/loaded latency, restore exact prior value and read back |
| `adapter.interruptModeration` | Driver interrupt batching trades CPU overhead for latency | Exact adapter GUID and driver-exposed supported property/value; service write | CPU increase, throughput regression, possible adapter restart | Supported property readback, repeated matched sessions, restore original property; restart only with authorization |
| `adapter.rss` | Spread receive processing when supported | Hardware/driver/OS capability and service authorization | CPU/throughput regression; driver-specific restart | Read effective RSS state and queues, match workload, restore and verify original state |
| `adapter.rsc` | Receive coalescing trades CPU work and delivery behavior | Capability per adapter and OS; service write | Workload-dependent latency/throughput trade-off | Read effective state, baseline-relative comparisons, exact verified restore |
| `dns.resolverSelection` | Resolver choice can improve lookup reliability/latency | Explicit authorization; exclude enterprise/VPN/private/split-horizon dependencies | Resolution failures and policy breakage; generally no restart | DNS-specific cached/uncached/failure tests; restore exact address list and DHCP semantics, not a guessed public resolver |
| `ip.pathMtu` | Diagnose a measured PMTU/fragmentation problem | Diagnosis first; family and interface capability; service write | Connectivity loss; family-specific behavior | Verify path and effective MTU, independent watchdog, exact prior-value rollback |

The initial enabled catalog is empty. Unsupported values, arbitrary registry paths, forced duplex, security-service changes, global Nagle tweaks, adapter disablement, and undocumented settings are not allowed. DNS performance must never be marketed as an established-session gaming RTT improvement.

The [read-only IPv4 packet-size diagnostic](packet-size.md) now collects controlled size-error evidence for MTU investigation. It does not establish a performance problem, generate an enabled candidate, or grant permission to change a setting.

## Diagnostic MTU proposals

The optional `automatic-trials` library now provides `experiment::candidate::proposeMtu`. Its trusted caller supplies a frozen cohort of two to eight distinct IPv4 destinations and complete controlled packet-size reports for every destination, with policy/native and selected-route evidence bracketing the entire sequence. It refuses missing reports, wrong sources or interfaces, changed routes/policy, disconnected links, clock inconsistencies, and evidence five minutes old. The cohort is fixed before diagnosis; dropping an inconvenient destination is not admission.

If every destination accepts its tested limit, no reduction is proposed. Otherwise the hypothesis uses the smallest explicitly confirmed boundary across the cohort, preserving the destinations that supplied size errors and a hash of all evidence. It uses the measured integer size, including non-preset values, rather than a list of gaming tweaks. Boundaries below the service's supported 1280-byte trial floor are refused. A successful larger size on another destination is not a claim that the proposed size was separately tested there.

The proposal exposes an immutable summary. Preparing a version-four checkpoint additionally requires fresh native and route captures, unchanged exact originals and policy, the same selected sources/routes, a valid owner SID, and a 5..300 second trial lease. A monotonic deadline and wall-clock high-water mark permanently end the proposal on expiry or clock rollback. Proposals cannot be reconstructed by deserialization. This constructs a checkpoint document; it does not persist a verified backup, issue a grant, apply or retain a setting. Tests feed its output through the existing adapter-scope and consent-preview validators without network writes.

An explicit size boundary can be ordinary Windows PMTU adaptation. This is a diagnostic hypothesis, not proof of a relevant performance problem, independent providers, stable internet paths, or improved gaming. Production still needs service lifecycle and storage integration, a demonstrated problem, complete profile guards, bounded session review, matched trials and confirmation, and independently verified recovery. Caller-supplied or desktop history is not authenticated service evidence; the normal pipe accepts no diagnostic bundle or automatic execution request. The enabled catalog remains empty.

## Service-side cohort collection

The optional library's `experiment::candidate::diagnosis::collect` captures its own IPv4 policy/originals and selected routes, runs the entire fixed cohort, captures routes and policy again, and calls the proposal validator. It selects each source from the captured route on the requested GUID. It accepts no caller-supplied source, native snapshot, packet protocol, executable, or command. The normal service pipe and desktop do not expose this operation yet.

A plan fixes two to eight destinations, a 35..300 second shared allowance, total probe attempts, and total requested IPv4 bytes. Each destination receives only the remaining traffic allowance, up to 144 probes and 1,296,000 requested bytes. The core refuses the next request before it would exceed either resource cap. An exactly completed cap is valid; spending the allowance does not invent an additional failed request. Sizes include IPv4/ICMP headers; replies and other wire/control overhead remain excluded. Time uses a monotonic deadline and wall-clock high-water mark. Sampling reserves sixteen seconds for final native verification and never extends the plan to finish another destination.

Full-size success completes diagnosis without proposing a reduction. A changed or unavailable final capture, incomplete target, cancellation, or observer failure returns stopped evidence with every available raw report and boundary capture. A fallible observer failure requests cancellation through the supplied control flag. The result is serializable for future service-owned storage; only a proposal's summary is exported, with no reusable runtime or authorization state. Returned evidence is currently in memory, not a durable crash journal or verified backup.

Tests use the real controlled diagnostic algorithm with simulated native capture/probe backends. Native account/physical-adapter integration, durable progress storage, and normal-service orchestration remain unfinished. The collector checks time and cancellation between native operations; it cannot independently preempt a blocked route API or progress consumer. Policy inspection retains its separate bounded owned worker. These checks do not establish a hard process deadline for the complete collector, installed-account compatibility, or a networking benefit. No settings or grants are changed.
