# Network settings backups and recovery

## Current snapshot workflow

Open **Saved settings**, select **Save settings copy**, and review the captured and unavailable sections. The application reads configuration, commits a new local snapshot, verifies its SHA-256 when opening/exporting it, and preserves earlier snapshots. **Download settings copy** downloads the exact saved JSON bytes; its filename includes the SHA-256 shown in the GUI.

Snapshots contain OS/build context, adapter GUIDs and driver versions, interface indexes, addresses and prefix origins, DHCP/IP interface settings, routes, DNS servers and client settings, TCP templates, and supported driver advanced properties/RSS/RSC/power settings. Driver properties preserve registry keywords and native values where exposed. Missing or unsupported sections retain their error instead of being reported as successfully captured.

Each settings record lists `unavailableFields` separately, preserving the distinction between a missing native property and an exposed property whose value is null. A captured section indicates that the reader returned data, not that every driver exposes every requested property.

The native DNS section reads `GetInterfaceDnsSettings` version one for each adapter GUID. It preserves the API's flags as a lossless hexadecimal string, adapter and profile nameserver strings, domain/search list, and registration/LLMNR fields. Null pointers remain JSON null; empty strings remain empty strings. Malformed UTF-16 makes the section unavailable instead of silently changing the value. Returned memory is freed even if serialization fails. Windows dynamically loads both getter and cleanup exports from the system directory; older systems or unsupported adapters record an explicit unavailable section without preventing the other snapshot sections from being saved.

Data is stored in the local application database outside the checkout. SQLite uses WAL, FULL synchronous mode, and a transaction that commits the settings document and its hash together. Snapshot records are appended, never overwritten by the capture workflow. Existing version-one application history survives the version-two database migration. The preview bounds each saved document to 2.5 MB and stops at 200 snapshots, preserving existing records. `clean.bat` does not remove the database or exported backups.

Backup history and export are local operations and remain available without internet connectivity. Exported files contain private network information and should be reviewed before sharing. A SHA-256 detects changed bytes; it does not authenticate an imported file or authorize restoring it. No backup import or settings-restore operation is enabled in this preview.

## Coverage limits

The desktop also appends `nativeIpInterface` sections for each inventoried adapter and IPv4/IPv6 family. GUID-to-LUID mapping is checked in both directions; native link and IP rows must agree on identity. The capture preserves all configurable `MIB_IPINTERFACE_ROW` fields, including MTU, automatic metric, router/host flags, zone indices, and default-route policy, together with link MTU/type/status. LUIDs are decimal strings so JSON consumers cannot round native 64-bit identities. OS context includes native version/build, update revision, and architecture. Driver context is matched by GUID to a unique present PnP device and includes package version, INF metadata, and device instance ID. Missing/ambiguous driver context is explicitly unavailable rather than guessed.

This native capture is part of the existing read-only snapshot and SHA-256 export flow. Cancellation or malformed extension data blocks finalization before storage. Collection is not atomic across OS calls; a service preparing a future experiment must capture and revalidate its own current state. `restorationVerified` remains false. Native rows do not prove persistent-policy-store origin, automatic/static DNS and addressing semantics, operation authorization, or a tested setter/restore path.

These are diagnostic settings snapshots. Automatic restoration is not implemented or tested. DNS server addresses alone do not establish whether the resolver configuration came from DHCP, static settings, enterprise policy, or VPN configuration. The native version-one fields add configuration evidence, but do not prove complete policy/DoH/IPv4/IPv6 origin or restoration semantics. The getter is initialized with only its version, as required by Microsoft; it does not set an IPv6 input flag or infer automatic DNS from IP DHCP state. Some drivers do not expose RSC, power-management, or RSS data. Collection runs over an interval and is not an atomic operating-system snapshot. These limits appear in each exported document and in the interface.

The application currently changes no Windows settings. Capturing a snapshot does not grant authorization to make changes and does not indicate that a proposed experiment is safe.

## Service checkpoint journal

The service now has a separate SQLite recovery journal library with immutable, checksummed MTU checkpoint documents and a chained event history. Each document records the exact original and proposed MTU, adapter GUID, address family, OS/driver context, authorized-user SID, creation time, and bounded lease. A SID written into a document is evidence, not an authenticated authorization grant. Only the future policy layer may authorize preparation; the current IPC protocol exposes no checkpoint writes.

Journal schema two adds a complete native original snapshot and native observations to version-two checkpoints. GUID, OS build/revision/architecture, PnP driver identity, family, and MTU capability must agree. Missing driver evidence blocks preparation. LUID/index may change across restarts when a fresh native lookup still proves the same GUID and context. Verified version-one journal history migrates without rewriting checkpoint documents; corrupt history is refused before migration. Older service binaries refuse the newer journal version. Documents and individual events are bounded to 16 KiB.

Journal schema three introduced [setting-process identities and a restart exit barrier](mutators.md), retained by schema four. Process registration must commit before execution; missing or unverifiable predecessors block observation and restoration. Migration preserves earlier checkpoint bytes and does not claim that legacy documents contain process evidence. Restoration also needs storage capacity for a new process record; failed registration preserves unresolved work instead of running an untracked command.

Preparation commits the document and initial event in one IMMEDIATE transaction using WAL and FULL synchronization, then reads them back. An apply intent requires a matching fresh original-value observation and a verified committed checkpoint. Readback gates applied, retained, and restored states. A changed GUID, OS, driver, address family, or unexpected third-party value blocks the transition. Expired leases permit cancellation/recovery only. Event sequence supplies ordering even after a backward wall-clock correction. Unresolved work blocks another experiment, stale writers cannot advance state, and terminal history cannot be reopened.

Startup validates SQLite identity/schema, integrity, foreign keys, each saved document, and every event hash/transition. The journal retains up to 2000 documents and 128 events per document; capacity or persistence failure blocks advancement and preserves evidence. SHA-256 detects corruption, not administrator tampering. The [service storage ACLs](service.md#recovery-journal-storage) establish the local ownership boundary.

Local tests use independent connections, reopen interrupted transactions, inject failed commits and corruption, reject changed adapter context, and terminate real subprocesses after committed apply/restore intents. The subprocess test changes a simulated MTU text file; it never touches a Windows adapter. This demonstrates journal persistence under process termination, not physical power-loss durability or native restoration.

The MTU coordinator library requires backend authorization before preparation, application, and retention, rechecks authorization after observation or durable intent, and requires fresh native readback before recording application or retention. Its backend is a typed Rust contract, not a command or IPC endpoint. The installed service now records temporary authorization through [authenticated previews](consent.md), but has no production native mutation backend. A preview/grant does not satisfy the durable-backup or fresh-apply checks.

Recovery does not require renewed apply authorization or an unexpired lease. A verified original record and durable apply intent allow exact-MTU rollback even when appending a restore event fails. Results separately report whether the original MTU was read back and whether recovery was durably finalized; a verified value with an unfinished journal remains pending. Recovery refuses an unexpected third-party MTU or changed identity. When unrelated interface fields drift, it restores only the MTU and reports the drift rather than reverting other software's changes. Real child-process termination tests exercise coordinator recovery after simulated apply and restore writes, including restart with expired authorization. These tests use a synced JSON adapter fixture and do not prove native restoration, reboot recovery, or Windows policy-store semantics.

Native MTU/interface/OS/driver readers are implemented. A disabled-by-default [native MTU lab](native-mtu-lab.md) passed twenty scoped IPv4/IPv6 loopback trials, including process termination during apply/restore, registered-command termination, deadline/heartbeat/shutdown recovery, automatic SCM crash restart, exact original MTU recovery, and unchanged unrelated fields, persistent policy, and DNS origin values. Exact durable lab grants, a service-owned watchdog, and temporary-trial coordination are implemented. A separate [repeated-trial runner](repeated-trials.md) now saves bounded matched-session progress. Production setter/privilege/consent integration, general persistent-versus-active MTU recovery semantics, DNS/addressing recovery, and reboot recovery remain unfinished. The normal service only initializes its journal and reports unresolved checkpoint counts; it does not claim `rollbackAvailable`. No diagnostic snapshot can substitute for these operation-specific recovery gates.

## Mandatory gate for future setting changes

### Service-owned registry origin evidence

New native interface snapshots use schema two and include `registryOrigins`. The service reads only the target GUID's `Tcpip` and `Tcpip6` interface keys, with nine fixed names: `MTU`, `EnableDHCP`, `IPAddress`, `SubnetMask`, `DefaultGateway`, `NameServer`, `DhcpNameServer`, `ProfileNameServer`, and `Dhcpv6DNSServers`. It records key presence, value presence, the original registry type, and exact hexadecimal bytes. Missing values, empty data, terminating nulls, binary data, and unexpanded strings remain distinct. It does not infer automatic DNS from IP DHCP state or turn an effective resolver list into a static configuration.

Two complete bounded reads must agree. Access failures, changing data, or more than four KiB of aggregate raw data produce an explicit unavailable result. Cancellation discards the capture. A schema-two native original with unavailable evidence cannot prepare a checkpoint; the existing durable commit, checksum, readback, GUID, OS/driver, and process-registration gates still apply. Strict observations and the final pre-command check reject origin drift. The native fixture's version-two environment fingerprint includes the origin evidence while excluding its candidate MTU. Its independent verifier additionally compares these fields in raw measurement receipts, saved original documents, and recovery observations.

Recovery remains MTU-specific. Unavailable current origin reads or external DNS/addressing changes do not require renewed apply permission and do not prevent verified original-MTU recovery when native identity remains established. Recovery preserves those external values and reports unrelated drift; it does not overwrite DNS or addresses. Such drift cannot become a clean completed trial. Legacy native-schema-one records remain readable and recoverable without inventing missing origin evidence. The current journal wrapper is version four; older service binaries refuse unsupported database or native snapshot versions rather than silently discarding evidence. Diagnostic backup JSON remains a separate read-only format.

This is fixed registry representation evidence, not a complete effective-policy capture, a supported registry setter, or proven DNS/addressing restoration. Group policy, per-network profile policy, encrypted DNS, IPv6 address configuration, persistent-store semantics, and physical/reboot recovery still need their operation-specific coverage. Diagnostic exports retain `restorationVerified: false`, list unavailable origin capture explicitly, and do not enable production changes. Registry data may include private addresses and DNS configuration; review exports before sharing.

The reader uses [RegOpenKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw) and [RegQueryValueExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw). It deliberately retains raw bytes rather than interpreting potentially unterminated strings or adding terminators. No registry write API or caller-selected path/value name is exposed.

### Read-only IP policy worker

The service executable accepts `--inspect-ip-policy GUID ipv4|ipv6` for an explicitly selected local adapter. It queries eleven fixed `MSFT_NetIPInterface` fields from ActiveStore and PersistentStore: MTU, interface metric, automatic metric, DHCP, router discovery, forwarding, weak-host send/receive, advertising, and managed/other stateful configuration. The result preserves unsigned CIM types, null values, and missing persistent rows separately. It includes native schema-two identity, registry origins, and OS/driver context; unavailable originals, ambiguous rows, nondefault compartments, or disagreement between active and native MTU cause refusal.

The worker uses local COM/WMI with current credentials and no setter, arbitrary query, remote namespace, or caller-selected field list. Native evidence must agree before and after enumeration. Its standalone command is not an added desktop/MCP operation or a complete DNS/addressing backup. Version-four checkpoint preparation and final policy readback use this reader; the critical native MTU recovery path does not depend on it.

The public inspection command now runs the raw reader in the same dedicated service executable as an owned, suspended child. Job assignment occurs at process creation, before any child code runs. Its anonymous kill-on-close job permits one active process, no ordinary descendants, and no breakaway. Only null input and a shared output/error writer are inherited; the job and pipe-reader handles are excluded. The parent drains output without a reader thread and refuses more than 64 KiB in total. Failed reads retain at most 1024 characters of error detail; successful reads must contain only complete valid JSON. It validates the exact requested GUID/family and capture schema before returning evidence. No caller-selected executable or arguments are exposed.

The raw reader's four-second enumeration allowance is checked between provider calls; individual COM calls can block longer. The parent enforces a separate fifteen-second collection allowance and cancellation, then permits up to five seconds to verify both a signaled process and zero active job processes. Handled failures and successful reads use that same exit barrier. Uncertain reader termination blocks further policy readers for that instance, including new version-four applies; it does not block the MTU recovery command. Uncertain setting-process termination still blocks all owned commands and native recovery observation. Abrupt owner death closes the noninherited job handle and ends its child, including before initial-thread resume. Only the owned reader is terminated; Windows' shared WMI provider is not targeted.

The smoke script independently checks both stores and families against `Get-NetIPInterface` and allows twenty-five seconds for the outer command, including worker cleanup. An explicit adapter GUID prevents fallback to a different interface. Hosted validation uses the native lab's newly owned Microsoft loopback adapter: a hosted virtual adapter without verified driver identity must remain ineligible. No production capture or checkpoint gate is relaxed for CI.

### Policy-bound checkpoint originals

New tracked checkpoint documents use version four and include `policyOriginal`: the exact active row plus a nullable persistent row, retaining CIM scalar types and null versus explicit values. Native schema-two GUID, OS/driver context, and registry origin evidence remain mandatory. The same checkpoint hash, durable transaction, committed readback, authorization binding, and registered-process chain cover this evidence. A missing policy original, unavailable provider, failed checkpoint commit, or mismatched current policy blocks preparation or application. Version-four evidence cannot be attached to an older checkpoint version.

Policy is checked before preparation, before apply intent, after committed apply intent, and before retention. A slow post-intent read must be followed by fresh native readback and renewed lease/authorization checks before writing. Only the active MTU value may differ during candidate comparison; stored MTU, missing rows, nulls, scalar types, DHCP, metrics, and all other fixed policy fields must agree. A changed interface index is normalized only after a fresh native lookup proves the same GUID and OS/driver context. New repeated trials require the template's exact policy cohort and cannot downgrade to an older checkpoint version.

Rollback first waits for registered setting processes, restores only the exact active MTU, verifies native readback, and records the MTU result. It does not require a policy query or renewed apply permission before that write. Final policy verification runs afterward, including on service shutdown. Changed or unavailable policy sets an explicit error and unrelated-settings warning while preserving the verified MTU result and external policy values. The trial controller refuses a clean completed trial in that case. A terminal `restored` checkpoint proves MTU recovery; it does not independently prove successful policy verification.

The SQLite journal wrapper is now version four, while native snapshot two, checkpoint document four, and status pipe two are unchanged. Older checkpoint documents remain readable without fabricated policy evidence; older binaries refuse the upgraded database. No DNS/addressing or persistent-policy setter is added. Physical/client-OS/reboot recovery, complete effective policy coverage, production authorization and mutation integration, and retained optimization still require validation. The normal application service remains read-only.

### Durable policy verification receipts

After a committed MTU `restored` event, the coordinator saves the complete policy readback or a bounded unavailable reason in a separate receipt chain. Each version-one receipt binds the checkpoint ID and document hash, exact restored-event hash, record sequence, prior receipt hash, recorded time, and a recomputed original-policy comparison. A transactional head/count and committed readback detect missing, changed, reordered, or incorrectly bound records. The chain contains at most sixteen records of at most 16 KiB each. Only version-four restored checkpoints can receive these receipts; a matching receipt closes that checkpoint's verification history.

Recovery results report `policyOriginalVerified` and `policyVerificationRecorded` separately. Failed policy storage cannot undo or prevent the already verified MTU rollback. It leaves the checkpoint pending for metadata verification, even though the MTU event is terminal. Missing, mismatched, and unavailable policy verification block a new checkpoint and repeated-trial measurements. Read-only retries wait for registered process identities, verify the original MTU, and retry policy capture without applying any setting or requiring an active apply grant. An unsuccessful retry preserves pending work; a successful committed receipt clears it. This is verification of the fixed captured policy at its recorded time, not continuous network health monitoring or permission to overwrite outside configuration changes.

Journal migration validates version-three mutator history before committing the new schema, preserves document/event/process bytes, and initializes empty receipt heads. Previously restored version-four documents therefore require a real policy check instead of inheriting invented success. Legacy documents without policy originals receive no fabricated receipts. Startup validates terminal histories as well as active recovery work. The native lab and library retry unfinished policy work after restart; production service recovery commands and a dedicated policy-status display remain unfinished.

### Production change requirements

Before any setter is enabled, the privileged service must perform all of these steps:

1. Match the target adapter by GUID and verify its current OS, driver, capability, management-policy, VPN, and remote-administration context.
2. Read the exact targeted original value, including absent versus present values and automatic versus manual DNS/addressing semantics. Reject the operation if required information is unavailable.
3. Commit a durable rollback checkpoint and intended operation record before making a change. Read back and verify the checkpoint. Failure to capture, persist, or verify it blocks the change.
4. Record explicit, expiring, revocable authorization for the specific allowlisted operation. A snapshot, AI proposal, or GUI session cannot grant extra permissions.
5. Apply the supported operation, read back the effective value, check connectivity, and run the matched measurements. Retain only after the required confirmation; otherwise restore the exact prior value and verify it.
6. Recover incomplete transactions through an independent service/watchdog after a GUI crash, service restart, reboot, deadline expiry, or connectivity loss. Report incomplete restoration explicitly.

Recovery must work locally, without an AI model or internet access. Provide original-configuration, last-known-good, and selected-checkpoint recovery only after the relevant operation's restore path has passed failure testing. Factory defaults and a generic adapter reset do not identify the user's original configuration.
