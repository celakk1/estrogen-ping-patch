# Repeated-session comparison library

The core comparison library analyzes complete original/candidate/original blocks. It is backend groundwork for the experiment engine, not a desktop optimization command. It does not run benchmarks, capture network settings, authorize changes, retain a configuration, or schedule experiments. The desktop remains a read-only preview.

## Evidence contract

A plan fixes the server cohort, environment identity, original and candidate configuration hashes, ordered metrics, metric directions, objective/safety roles, measurement resolutions, practical thresholds, regression limits, baseline-drift limits, and maximum matched-block duration. The duration must be explicitly bounded within one day; this upper input limit is not a recommendation for widely separated measurements. It requires at least one objective and one guard. No universal score or default percentage weights combine unrelated measurements. Thresholds are explicit inputs; production profiles and validated defaults remain unfinished.

Each matched block contains one completed original session before the candidate session and one completed original session afterward. Session IDs must be unique across the comparison, timestamps ordered and nonoverlapping, and all hashes/metric counts consistent. Missing, nonfinite, negative, unfinished, reused, or mismatched evidence is refused. The limit is 128 blocks and 1024 metrics. One block contains three sessions, regardless of the number of packets within them.

The original reference is linearly interpolated between the midpoints of the surrounding original sessions at the candidate midpoint. This accommodates unequal spacing; it does not establish that real drift is linear. A surrounding-baseline change beyond the configured absolute/relative drift allowance, floored at measurement resolution, invalidates the complete comparison. Bad blocks are not silently discarded. Unexpected environment/cohort changes are rejected before analysis.

Benefits have the metric's original unit, with positive values always meaning improvement. Thresholds use the greater of the absolute allowance and the baseline-relative allowance. Practical improvement must be at least the declared measurement resolution. Any observed block exceeding a hard regression limit rejects the comparison, even if the average is better or there are too few blocks for inference. Results preserve the complete plan and block evidence, per-metric effects, limits, and offending block indexes.

## Uncertainty and outcomes

At least twelve complete blocks are required before resampling. This is an engineering minimum, not a guarantee of sufficient power or independence. Analysis uses 16,384 bootstrap resamples of whole matched blocks; all metrics use the same selected block indexes. For each metric, it resamples the benefit, benefit minus its practical threshold, and benefit plus its regression allowance. Relative thresholds travel with their original session rather than being treated as fixed averages. The three reported intervals per metric use a nominal confidence of `1 - 0.05 / (3 * metricCount)`. The simultaneous nominal level is 95 percent. The adjusted intervals concern the configured metrics within one comparison, not repeated candidate searches or repeated looks at accumulating data.

The [SciPy bootstrap documentation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html) describes paired resampling and percentile intervals, while also explaining that basic and BCa methods are more common. The [NIST Bonferroni description](https://itl.nist.gov/div898/handbook/prc/section4/prc473.htm) motivates the per-metric confidence adjustment. Bootstrap coverage remains approximate; adjustment does not repair dependence between sessions, biased cohorts, inadequate data, or an invalid underlying interval.

A deterministic SHA-256 counter stream selects unbiased block indexes with rejection sampling. Its seed is the SHA-256 of the serialized plan and block evidence, retained as `evidenceSha256`. Reanalysis of unchanged input reproduces the same report. The digest detects changed evidence; it does not authenticate an untrusted producer or establish that the plan was committed before collection.

| Outcome | Meaning |
| --- | --- |
| `invalid` | At least one bracketing baseline drifted beyond its allowance |
| `reject` | At least one observed block exceeded a hard regression limit |
| `inconclusive` | Too few blocks, insufficient effect, uncertain safety, or degenerate resampling |
| `promising` | An objective's practical-margin interval is entirely positive, every metric's non-regression-margin interval meets its gate, and no observed hard regression occurred |

All reports explicitly remain exploratory. Degenerate distributions cannot become promising, including a safety metric that never varied; repeated observed zero failures alone is not a validated rare-failure upper bound. `promising` means eligible for further investigation, never permission to retain. Independent confirmation, calibrated coverage/power, serial dependence, rare failures, sequential testing, multiple candidates, production profile policies, and final retained-configuration verification remain required.

## Existing baseline adapter

`comparison::baseline` converts saved completed TCP, ICMP, or DNS runs into session measurements. It hashes exact endpoint metadata, application version, sample count, pacing, timeout, session time budget, and metric selections into the cohort. Changed selection order or measurement policy changes the hash. It validates raw sample protocol/outcome consistency, addresses, timestamps, balanced endpoint counts, and configuration/context binding, then recalculates selected statistics from raw samples rather than trusting stored summary fields.

Available selections are median, p95, p99, IQR, successive variation, and protocol-specific failure/timeout percentage. ICMP OS errors cannot become zero loss, DNS negative-answer timing cannot become successful lookup timing, and whole-millisecond ICMP cannot claim a finer comparison resolution. Missing required metrics prevent comparison instead of becoming zero. This adapter does not establish tail-estimate precision from a small packet count.

Environment and network-configuration hashes must come from a trusted collector that verifies the exact operation and relevant adapter, OS, driver, routing, VPN, and policy context. The existing desktop baseline format has no such capture stamp; the adapter requires it separately and cannot invent it from benchmark options. The optional service [repeated-trial host](repeated-trials.md) now links matched sessions to the verified MTU trial controller. A complete production collector bound to that checkpoint and measurement lifecycle is still unfinished. UI/report history integration remains unfinished. No persistent database or IPC format changed for this comparison library.

New desktop baselines preserve [selected local route evidence](routing.md) at the measurement boundaries. When present, changed, unavailable, inconsistent, or unsupported route evidence blocks conversion even if the caller supplies a matching context hash. This is partial diagnostic coverage, not the complete environment/configuration stamp required here. The adapter does not substitute a route fingerprint for either required hash. Older records still require the separate trusted context described above.

## Source-bound load adapter

`comparison::load` converts complete saved source-bound load sessions into the same matched-session format. Its cohort includes the exact application version, complete configuration and load plan, ordered provider/echo bindings, and metric selections. It recomputes download/upload Mbps from raw stream payload totals and elapsed time, and phase median, p95, p99, interquartile RTT spread, successive RTT variation, and timeout percentages from raw echo samples. Cached goodput and latency summaries do not supply comparison values.

Both transfer directions must complete for every provider, with consistent provider identity, exact stream ordering and split byte counts, bound peer/source, HTTP status, timing, and error-free completion. Raw probes must retain valid endpoints, protocol/outcome consistency, chronological provider/phase order, quiet-phase counts, bounded request counters, and progress totals within the phase's payload. At most 4096 raw probes can be admitted. A qualifying loaded probe must fit its recorded transfer window, allowing its configured probe timeout and 250 ms of end-boundary tolerance. This check does not establish link saturation or uninterrupted internet-path stability.

Selected latency/failure metrics require at least twelve qualifying attempts; every RTT statistic additionally requires twelve successful replies. Loaded comparisons require a request active at both probe boundaries. Payload progress alone or a partial request overlap remains in the raw run but cannot supply those values. This is stricter than the ordinary diagnostic table's overlap selection. These data floors do not establish statistical calibration or independence. Short transfers without sufficient overlap remain unsuitable for comparison. Failure rules are guards with a percentage resolution no finer than one observed attempt; ICMP latency rules retain the one-millisecond native resolution. Metric order, units, directions, context/configuration hashes, and the 1024-metric plan limit remain mandatory.

`IqrMs` is the 75th percentile minus the 25th percentile of qualifying successful native RTTs, using the existing interpolated quantiles. `SuccessiveVariationMs` is the mean absolute RTT difference between adjacent successful qualifying probes for the same provider, phase, and endpoint. Timeouts and recorded probes without full request overlap remain gaps; the calculation never joins replies across those gaps. At least eleven valid adjacent reply pairs are required, in addition to twelve successful replies. These statistics are available in all four phases and retain milliseconds and lower-is-better rules. They describe RTT variability, not one-way packet-delay variation, link saturation, or a calibrated guarantee about gaming stability. A sample floor is not a confidence interval.

`MedianMs` and `P99Ms` use the existing interpolated quantiles of qualifying successful replies, separately for each frozen provider, phase, and endpoint. They retain the same twelve-reply data floor and native one-millisecond comparison resolution. Fractional quantile estimates do not establish fractional native timing precision. In particular, that floor does not establish a precise p99 estimate or a sufficiently sampled production tail-latency guard; sampling/uncertainty calibration remains required. Changing between median, p95, or p99 changes the comparison cohort, even with the same metric identifier. Missing or unqualified samples cannot become zero RTTs.

The extra statistic selections change the cohort hash. Existing selections retain their serialization and hash preimages. Raw load-session payloads, application database six, and service wire protocol four are unchanged; older comparison code refuses unknown statistic variants rather than interpreting them as another metric. Service receipt admission enforces the same native millisecond resolution for these selections. Complete profile coverage, sufficient sampling policy, and production session integration remain unfinished.

The adapter is not a settings backup or authorization source. The optional [service load collector](repeated-trials.md#adapter-bound-load-collector) now derives local sources from selected routes and requires bracketing native/policy evidence, frozen traffic declarations, exact checkpoint identity, and durable raw/receipt readback. Production service-protected storage/session integration must still establish provider eligibility, complete profile guards, recovery, and independent confirmation before an automatic decision. Caller-edited desktop history or supplied hashes do not establish that trust. Production loaded execution and automatic retention remain unfinished.

## Profile objective admission

Load conversion and service load-plan binding now enforce the selected profile's primary objective family. The profile is part of the frozen raw configuration and comparison cohort. Changing a metric's role cannot make an incompatible objective eligible.

| Profile | Eligible objectives | Other selected measurements |
| --- | --- | --- |
| Latency | Median/p95/p99 RTT, IQR, successive RTT variation | Throughput and failure rates remain guards |
| Balanced | RTT/variation, download/upload throughput | Failure rates remain guards |
| Download | Download/upload throughput | RTT/variation and failure rates remain guards |

At least one objective and one guard remain mandatory. An objective outside the permitted family rejects the plan even when another eligible objective is present. This prevents a throughput-only gain from promoting a Latency trial or a latency-only gain from promoting a Download trial. Every metric still has its own explicit practical-improvement, maximum-regression, and baseline-drift limits; objective metrics retain their regression checks. No universal score or new percentage weights are introduced.

The optional service's echo-only trial collector additionally refuses the Download profile before native inspection, because it cannot measure a transfer objective. Ordinary desktop connection tests and the general read-only baseline adapter remain available for diagnostics.

These objective-family checks remain separate from required measurement coverage. Existing raw reports remain readable; conversion refuses profile-incompatible objective selections. No setting, grant, or retention authority is added.

## Four-phase load safety coverage

The optional service load collector now requires the same complete set of currently supported measurements for every profile before native capture, source binding, or recording initialization. `comparison::load::requiredSafetySelections` produces the typed set; `validateSafetyCoverage` checks every provider, destination, phase, and statistic without depending on display identifiers.

For every provider, the set includes download and upload goodput. For each of that provider's latency destinations, all four phases require median, p95, p99, IQR, successive RTT variation, and failure percentage. Objective eligibility still follows the selected profile; every selected metric retains its own hard-regression and baseline-drift limits. Missing or semantically duplicated measurements reject the plan. A second destination's upload or recovery failures cannot be omitted just because the first destination's download objective improved.

The count is `providerCount * (2 + 24 * endpointCount)`. One provider and two distinct latency destinations require fifty metrics. The 1024-metric comparison bound accommodates the factory's full four-provider/eight-destination set of 776 measurements. The existing two-destination minimum, 250 ms pacing minimum, and service collector's five-minute trial limit with thirty seconds of verification headroom remain unchanged. Timing admission still applies: four providers with eight destinations need at least 384 seconds of sampling and cannot run as one setting trial. Such plans are refused before native capture rather than silently dropping servers or weakening pacing. Controlled fixtures cover four providers/four destinations, two/eight, and three/six within valid time allowances.

The general core adapters still support explicit partial selections for read-only diagnostic analysis. The service's setting-trial collector enforces the stricter coverage gate. The selection set and order remain part of cohort hashing, and thresholds remain explicit reviewed inputs. Old raw sessions and database/wire schemas are unchanged. Older comparison code refuses plans above its former bound; it does not truncate their metrics.

The existing resampling method adjusts its nominal family intervals to the actual metric count, including all three margins per metric. All results remain exploratory: wider families, sufficient tail precision, dependence, rare failures, and independent confirmation still need calibration. A 1024-metric regression fixture checks the final guard and family adjustment, while a thirty-two-block/1024-metric persistence fixture checks the four MiB experiment limit. Those tests do not establish statistical coverage or a performance benefit.

This gate covers the four implemented phases and available raw metrics. Multi-session orchestration for cohorts that cannot fit one trial, simultaneous load, sustained single/multi-stream behavior, retransmission and CPU guards, sufficiently sampled tails, demonstrated-problem admission, production storage/recovery, and review/execution integration remain unfinished. Production optimization stays disabled.

## Bounded analysis and cancellation

Resampling retains at most 48 distribution series at once: six MiB of `f64` distribution payload. A shared byte-index draw table adds at most two MiB at 128 blocks. These bounds describe resampling buffers, not total process memory. Every batch replays the same seeded draws, preserves summation order, and uses the whole family's error adjustment. Tests compare interval bits with the original monolithic algorithm across batch boundaries, including degenerate series and paired opposite metrics.

`analyzeWithCheck` accepts a fallible control check before allocation, during draw preparation and resampling, between distribution sorts, and before returning. A refused check returns an error without a partial statistical report. The ordinary `analyze` entry point remains available for read-only analysis with fixed input/work bounds. A control callback must return promptly; these checks do not independently preempt callback code or operating-system scheduling.

The repeated-trial runner commits each completed bracket before analysis, then uses its existing cancellation, wall-clock, and monotonic deadline checks while computing. It retains the last successfully checked comparison and returns that result after final original verification. It does not repeat resampling after finalization. If a newer comparison is interrupted, no older comparison is substituted for the newly completed block set; committed raw blocks remain available. A cached exploratory result does not override a cancelled/expired experiment state or authorize retention. Startup retains its existing interruption/recovery gate and does not resume analysis or trials automatically.

## Validation

Seventeen focused tests cover paired-block resampling, an exact binomial fixture for interval bounds, opposite-metric index pairing, reproducibility and evidence round trips, insufficient sessions, hard regressions despite a better average, complete-comparison drift refusal, uncertainty/degeneracy, timestamp precision, input bounds, and context/cohort mismatch. A targeted failing test reproduced false promotion when relative-threshold uncertainty was ignored; it passed after practical and non-regression margins were resampled together. Baseline tests recalculate deliberately false saved summaries, reject inconsistent or reordered raw evidence and recorded route failures, preserve ICMP/DNS outcome semantics, and convert actual loopback TCP measurements after SQLite persistence. The loopback test verifies the adapter execution path, not internet performance or optimization efficacy.

The initial sixteen-test library milestone at `ce0e2b8` passed the [full hosted Windows pipeline](https://github.com/celakk1/estrogen-ping-patch/actions/runs/41267410460), including production packaging, packaged desktop/MCP checks, and temporary installer lifecycle. That run predates the local-route evidence and admission extension. It does not establish statistical calibration or production experiment orchestration.
