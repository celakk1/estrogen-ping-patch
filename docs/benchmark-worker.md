# Bounded transfer worker

## Status and purpose

The optional adapter-bound load collector now delegates HTTP transfers to a restricted worker. The owned-process boundary, sealed request, bounded live frames, shared atomic probe counters, and execution-specific comparison cohort are implemented. A bounded public HTTPS download and certificate-name rejection passed with the worker's separate TLS backend. Manual desktop diagnostics retain their direct implementation. Installed-account and broader TLS validation, plus production optimization, remain unfinished.

Native route, adapter, policy, checkpoint, watchdog, and journal ownership stay in the service. HTTP/TLS parsing must run in a separately bounded worker with no setting, authorization, journal, arbitrary-command, or path capability. The core session observer can keep its bounded source-bound echo sampling while delegating only `TransferPlan` plus its frozen `SourceBinding` to this worker. Manual desktop diagnostics retain their existing implementation.

## Required execution boundary

- The core provides `BoundTransferRunner` and `runSourceBoundSessionWithRunner`, including runner-owned progress creation and checked snapshots at probe boundaries. Existing entry points retain the direct runner. Binding validation precedes execution, and changed result plan/provider/source/peer is refused. Progress preparation and observation errors remain phase errors in the returned raw run without direct-HTTP fallback. This contract alone is not a process boundary or a complete untrusted-result validator.
- Launch only the known service worker image and fixed typed mode. Job assignment must remain atomic at process creation, with kill-on-close, one active process, no breakaway, and verified termination before a returned result is admissible.
- Create a restricted primary token rather than inheriting service authority. Disable administrative identities and privileges, apply a restrictive SID list and low integrity, and validate the resulting token in the worker. Fail closed without an unrestricted fallback.
- Keep recovery and authorization storage inaccessible to the restricted worker. Test actual access denial, not only token flags. Existing installed binary permissions grant authenticated users read/execute; this does not grant them access to the protected recovery directory.
- Provide a minimal environment and fixed system working directory. Do not pass the service's environment, credentials, private configuration, journal handles, job handle, or pipe-reader handle to the worker.
- Apply job UI restrictions as well as the process-count limit. No benchmark worker needs desktop handles, clipboard access, or Windows configuration controls.

Microsoft documents that [restricted tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens) require both ordinary and restricting-SID access checks to succeed. [`CreateRestrictedToken`](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken) can disable SIDs and privileges; its maximum-privilege flag preserves change-notify privilege. [`CreateProcessAsUserW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw) supports a restricted version of the caller's primary token. These API contracts do not prove this application's isolation, network compatibility, or installed-service behavior; those require actual Windows checks.

## Implemented optional boundary

The `automatic-trials` build includes `transfer_worker::measureFrom`, `IsolatedTransferRunner`, and a fixed `--transfer-worker LENGTH PARENT_PID PROGRESS_HANDLE` mode. The parent selects only its own canonical service image; executable paths are not accepted by an IPC operation. Before parsing its input, the child verifies its restricted token, low integrity, deny-only administrative/System identities, and removal of privileges other than change-notify. Its restricting list contains Everyone, Authenticated Users, built-in Users, and Restricted Code. It excludes logon, original-user, and service SIDs. The newly created token's default object descriptor grants the original owner and Restricted Code access, with explicit owner-rights handling. This permits worker-created objects and self-token queries without granting the parent's logon identity. Parent and linked-token descriptors are not modified. Missing or unexpected identity information fails closed.

The generated parent PID is additional read-only startup metadata. Before reading request bytes, the child verifies access denial for opening that parent's token with query, duplicate, assign-primary, and impersonation rights individually. Even a query handle must be refused because handle expansion can grant more rights for some object types. Unexpected access-check errors also stop startup; the guard does not infer safety from an unavailable or malformed parent identity.

The child receives only the explicit request, counter-page, output, and NUL handles. Its environment contains SystemRoot and WINDIR, with the system directory as its working directory. Its job permits one process, limits process commit to 256 MiB, applies all job UI restrictions, and kills the process when its owner closes the job. Restricted workers use detached execution: invisible-console initialization failed before Rust startup under these restrictions. Normal policy and recovery command launch behavior is unchanged.

Local child tests verified refusal of protected event access, private-file reads/writes, parent-process memory reads/writes and handle duplication, parent-token authority, descendants, and a 300 MiB allocation. Linked-token tests distinguish identification-only tokens from usable authority and try both handle expansion and token-type conversion. They also verified the minimal environment and fixed working directory. An earlier logon-restricting identity permitted parent-token reopening and was removed after an actual failing regression. This is evidence for the current interactive account, not installed LocalService/System or physical-adapter validation.

## Input and result protocol

Use one bounded, immutable typed request per process. It contains the schema, transfer plan, and exact local-source/numeric-peer binding, not a shell command or an entire application configuration. Keep request data out of command-line arguments and temporary user-owned files. Pass only the specific input capability and output writer through the existing explicit inheritance list.

The optional worker uses a schema-one request of at most 8192 bytes in an anonymous memory mapping. The parent fills and verifiably unmaps its writable view, closes the writable handle, and inherits only a read-only duplicate. The descriptor allows the restricting identity read access and prevents implicit owner permission changes. A read-only duplicate alone is insufficient: [`DuplicateHandle`](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle) can grant additional rights for some object types. Before parsing, the actual child requires access-denied results for direct write mapping and duplication with write, WRITE_DAC, or WRITE_OWNER rights. Other errors also block execution. These checks passed locally, and the parent retains its independent frozen request.

The optional entry point returns version-one JSON-line frames with contiguous sequence numbers. Each line is bounded to 64 KiB; the complete stream is limited to 4096 frames and 4 MiB. Every 25 ms the worker checks its actual payload and active-request counters, emitting a progress frame only when that tuple changes. Polling alone never emits an unchanged-counter heartbeat. A final changed observation precedes the single terminal result. The parent incrementally validates framing, exact fields, versions, sequence, monotonic payload/time, direction, request activity, and the frozen traffic allowance. Terminal counters must match the streams exactly, and all trailing data is refused.

The parent requires zero exit and verified process/job shutdown before returning the terminal result. It rejects changed plan/provider/source/peer, incorrect stream counts/ordinals/request splits, contradictory payload counters, invalid durations/timestamps, and inconsistent status/goodput summaries. Cancellation and the complete phase deadline include process startup. `measureWithProgress` exposes provisional observations with worker-relative elapsed time and the parent's receipt instant. Callback refusal or panic terminates the owned worker before control returns. A terminal failure retains its explicit raw stream outcomes rather than inventing progress or success.

Pipe observations remain delayed and provisional. They never update probe counters or establish when payload moved relative to a native probe. Instead, each phase receives a fresh anonymous 32-byte mapping containing a version marker and three aligned atomic counters. The worker's actual transfer implementation updates those atomics directly. The parent reads them at native probe boundaries, with direction, byte, request-count, regression, and schema checks. A terminal result must agree with both the frame stream and shared counters after verified shutdown. The worker requires zero-initialized counters and refusal of descriptor/owner escalation; completed counter storage cannot be reused.

The counter capability grants read/write mapping access to this separate low-integrity object, while request bytes remain immutable. Both views are writable because Rust's sequentially consistent atomic loads cannot generally be used on read-only pages. The mapping contains no pointers, configuration, journal state, or setting commands. Its reference-counted owner keeps each view alive through transfer futures and uploads. This follows [Windows shared-memory mapping](https://learn.microsoft.com/en-us/windows/win32/memory/sharing-files-and-memory) and [Rust's atomic access requirements](https://doc.rust-lang.org/std/sync/atomic/index.html#atomic-accesses-to-read-only-memory); the actual executable tests provide application-specific evidence.

`IsolatedTransferRunner` supplies these counters to the core observer. Standalone isolated sessions carry `transferExecution: restrictedWorkerV2`, covering the fixed restricted process policy, shared-counter method, and separate TLS backend. The adapter-bound collector wraps that runner with synchronous durable progress recording and uses `recordedRestrictedWorkerV1`; this additionally separates the observer's storage overhead from unrecorded sessions. Change the corresponding version whenever those semantics change. Comparison cohorts bind the execution version. Legacy/direct and earlier worker reports remain readable, but this collector refuses them. Its cancelled blueprint and actual collection use the same recording runner. Existing overlap rules still require active requests at both boundaries; this does not establish saturation or payload movement during every probe. Preserve incomplete raw evidence when a worker stops, while refusing it for comparisons.

The parent enforces its phase/session deadline and cancellation independently of the worker's runtime or HTTP timeout. Receiving a terminal frame is insufficient: require valid framing, zero exit, verified job quiescence, and the existing native and durable measurement admission checks. On worker failure, never retry an endpoint, bind another source, accept cached summaries, or enlarge the approved traffic budget automatically.

When an isolated phase returns an error to a living collector, its optional `interruptedProgress` records either a checked counter snapshot with the parent's capture time or a bounded explanation that counters were unavailable. Capture happens before the final progress callback. This is incomplete diagnostic evidence: bytes are not accepted HTTP payload or a speed result, and an old active-request count does not establish worker liveness after termination. Comparison admission refuses any transfer carrying this field, even if its other fields claim completion. Direct and older reports keep the field omitted.

The existing raw-session save/history path preserves this evidence across database close/reopen. The optional collector now additionally commits a [progress journal](load-recordings.md) before traffic and at each session progress callback. An owner crash preserves the committed prefix, not observations between callbacks or an unsaved final report. Interrupted recordings cannot become comparison evidence or resume an experiment.

## TLS backend and manual smoke

The initial actual HTTPS check failed before payload reception with Schannel `SEC_E_NO_CREDENTIALS` under the restricted token. A source-bound control request succeeded. The installed native TLS library already sets `SCH_CRED_NO_DEFAULT_CREDS`; removing the token restrictions or restoring the unsafe logon SID was not an acceptable fix.

The optional `isolated-tls` core feature now selects Rustls with an explicit ring cryptography provider for `measureIsolatedFrom`. The worker uses this fixed entry point. Ordinary transfer entry points explicitly retain native TLS, including when Cargo unifies both backend features. Rustls uses the [platform verifier's Windows certificate store and verification APIs](https://github.com/rustls/rustls-platform-verifier), with certificate and hostname checks enabled. There is no custom root, credential forwarding, certificate bypass, or runtime TLS-selection field. Reqwest documents [explicit backend selection and custom crypto-provider features](https://docs.rs/reqwest/0.13.5/reqwest/tls/). The worker's execution version advances to two so comparison cohorts cannot silently mix the different backend policies.

The separately selected ignored test `transfer_worker::tests::manualPublicTlsSmokeUsesOneBoundedCloudflareDownload` requires `EPP_PUBLIC_TLS_SMOKE=cloudflare-1024-byte-download` and the previously described `EPP_TRANSFER_WORKER_IMAGE`. It resolves Cloudflare's documented hostname, uses the current IPv4 source route, and makes one 1024-byte download with one stream and a five-second phase limit. It additionally tries the same peer with a numeric certificate name and requires a certificate-related failure with no accepted payload or HTTP status. Both checks passed under the restricted token. This is a manual public-network test; the ordinary `test.bat` selection excludes it and continues using loopback only. Its payload cap does not include DNS, TCP/TLS, or operating-system certificate-validation traffic.

## Validation still required

Actual restricted-worker IPv4/IPv6 loopback downloads and uploads passed locally, as did stalled-request deadline/cancellation, parent death before/after resume, and malformed terminal-result checks. Live download and upload observations arrived while the fixture prevented transfer completion until the callback released it. Refused and panicking progress consumers both closed actual stalled worker traffic before return or unwind. Shared counters continued advancing while the parent's frame callback was blocked, and a complete source-bound session observed live request counts during both transfer directions. A cancelled session retained exactly 1024 observed download bytes across a real database close/reopen, with socket closure independently checked. Four deliberately unsafe request capabilities were refused: direct writes, duplicate-handle write expansion, DACL changes, and ownership changes. No service installation or network configuration change was involved. Ordinary `test.bat` runs token/capability and protocol validation, builds the optional worker in `target/transfer-worker-tests`, and explicitly selects the eight executable integration tests against that image. This keeps optional worker artifacts separate from normal application service builds and never selects native setting helpers. For a separate manual run, build the service with `automatic-trials`, set `EPP_TRANSFER_WORKER_IMAGE` to its absolute executable path, and select the ignored `transfer_worker::tests::isolatedWorker` tests.

Still verify restricted-worker flooded output, installed protected service files and token behavior, broader certificate failures and trust-policy compatibility. Protocol tests cover frame/stream limits, arbitrary chunk splits, malformed fields, counter/time drift, and callback refusal; existing general owned-process tests cover flooded output. Those do not replace a restricted-transfer flood fixture or installed-account checks. One successful public TLS path and a certificate-name refusal do not establish every certificate or account configuration.

Installed LocalService and recovery-account behavior, client Windows versions, broader TLS/ICMP compatibility, physical adapters, actual provider eligibility, and installed-service crash integration of progress recording remain unverified. Synthetic killed-writer tests cover the journal's committed prefix and discarded uncommitted tail. The last hosted CI attempt was refused at the account billing/spending boundary recorded in [validation](validation.md); do not substitute hosted success from an earlier revision for these remaining checks. Do not install a service or change development-machine network settings to bypass those limits.
