# Development plan and acceptance tracking

The complete product scope is [the supplied master specification](specification.md), plus the Windows execution and private-repository requirements described in the README. A working baseline preview is a milestone, not completion of the optimizer.

The owner's clarified product direction is system-wide networking optimization with gaming responsiveness as a core constraint. There must be no required game selector or "boost this game" workflow. Use actual networking benchmarks rather than measuring ping inside games: unloaded RTT, jitter, protocol-specific loss, DNS, throughput, and loaded responsiveness across multiple benchmark endpoints. Do not require game integration or gameplay telemetry. Improvements must be demonstrated across the stable benchmark cohort, with regressions checked before retention; no universal improvement across every game or route may be assumed.

## Acceptance evidence required

1. Read-only inventory: compare Windows cmdlets and GUI data on Ethernet, Wi-Fi, virtual adapters, VPN, IPv4-only, dual-stack, and multiple-interface machines.
2. Measurements: deterministic adapter tests plus permitted live checks for latency, jitter, loss, loaded responsiveness, throughput, and errors across independent providers. Protocol labels must match actual measurements.
3. Optimization: real supported candidate application, effective-value readback, repeated matched sessions, baseline drift rejection, statistically and practically justified retention, and exact verified rollback.
4. Recovery: service and desktop crash injection, service restart, reboot, connectivity failure, disk-full and locked-database cases, operation deadlines, and manual offline restore.
5. AI: invalid proposal rejection, no arbitrary commands/files/endpoints, expiring authorization, disabled/local/cloud/automatic modes, secure secrets, budget/rate limits, and deterministic continuation on provider failure.
6. Scheduling: persistent immediate, timed, recurring, idle/AC-only sessions, stop time, metered/cellular safeguards, resource-aware pauses, and byte/bandwidth/provider budgets.
7. UX: all three profiles, configurable duration, actual live progress and adaptive ETA, experiment explorer, settings, reports, JSON/HTML exports, and honest inconclusive/no-improvement outcomes.
8. Delivery: six functional batch files, clean-clone setup and launch, release executable and installer, shortcut-based terminal-free launch, safe cleanup, automated CI, private GitHub main with verified expected files, and a staged secret scan before commits.

## Contributor workflow

Use camelCase variables, functions, and fields except externally mandated names. Preserve Rust type/module/constant conventions and serialize public JSON as camelCase. Comments must be minimal and lowercase. No emojis in workspace files or commit messages. Preserve unrelated changes and avoid broad formatting/refactoring.

Optional adapter-bound echo and load collectors now preserve native policy/route evidence, exact candidate checkpoint identity, fixed source bindings, and durable raw/receipt readback. Raw load conversion recomputes metrics and refuses inadequate request overlap or successful replies. These are internal library components; production service session/storage/worker integration, complete profile guards, candidate generation, calibrated confirmation, and retention remain unfinished.

Successful optional transfer workers now include [parent-owned process CPU evidence](benchmark-worker.md#parent-owned-process-cpu-evidence) captured after verified exit and separate [system CPU boundary snapshots](benchmark-worker.md#system-cpu-boundary-evidence). Exact raw counters and explicit unavailable reasons survive session history. System capture refuses unsupported processor coverage and advances execution cohorts while retaining historical recordings. These are raw process/system counters; calibrated CPU guards, peak detection, separate driver accounting, scheduling admission, and production optimization remain unfinished.

The service load planner now enforces [all currently supported four-phase safety measurements](comparisons.md#four-phase-load-safety-coverage) before native capture and recording. The 1024-metric bound accommodates all declared provider/destination combinations, with bounded resampling buffers and interruptible analysis. Actual trial admission also preserves pacing, lease, and verification headroom: controlled fixtures cover four providers/four destinations, two/eight, and three/six, while an over-budget four/eight session is refused before native capture. Every direction, destination, and phase remains in the frozen cohort. Multi-session orchestration for larger workloads, simultaneous load, sustained/transport/resource guards, sufficient tail sampling, and calibrated production admission remain unfinished.

The optional adapter-bound load collector now uses a [restricted transfer worker](benchmark-worker.md) with a sealed request, bounded versioned frames, independent process cleanup, and shared atomic counters read at probe boundaries. Saved sessions bind the execution version into their comparison cohort; legacy/direct evidence is refused by this collector. Actual source-bound IPv4/IPv6 transfers, stalled cancellation/deadline, parent-death, consumer refusal/unwind, blocked frame delivery with advancing shared counters, and full probe sessions passed locally. A manual bounded public HTTPS download and certificate-name rejection passed using the worker's separate Rustls backend and Windows certificate verifier. Version-two cohorts distinguish that backend from the earlier Schannel policy. Failed isolated phases additionally preserve checked, explicitly incomplete counters or an unavailable reason in saved raw reports; a real cancellation/database-reopen test passed. The collector now also keeps a [durable progress journal](load-recordings.md), uses a separate recorded-execution cohort, and atomically links final raw reports. Synthetic killed-writer tests preserve committed progress and discard an uncommitted tail without resuming work. Installed-account and broader TLS checks, installed-service crash integration, and production integration remain unfinished. Production optimization stays disabled.

Current measured evidence and its limits are recorded in [validation](validation.md).

Selected-route captures now also preserve [raw adapter statistics](routing.md#adapter-statistics) from their existing native link query, including exact counters, reported link state/speed, and query timing. Changing counters stay outside route fingerprints. History, wide recording headers, and load receipts retain these observations; these raw observations alone do not provide utilization or complete resource admission.

The optional load collector now requires five [reported adapter error/discard guards](comparisons.md#reported-adapter-count-guards), freezes the reported link context into its cohort, refuses observed resets/inadequate payload accounting, and records the extracted counts in schema-two native receipts. The complete trial vector is the transfer selection count plus five, without additional measurement traffic. These guard values reach the repeated-trial regression checks. CPU/utilization and transport guards, physical-driver qualification, transient reset/reconnection detection, calibrated confirmation, and production integration remain unfinished.

The optional service library also derives [diagnostic MTU proposals](candidates.md#diagnostic-mtu-proposals) from complete controlled multi-destination evidence with stable native policy and routes. Its collector captures its own originals/routes, shares explicit probe/byte/time limits across destinations, and preserves partial results on stop or failed final verification. Native route capture and packet probes run in [separately bounded owned workers](diagnostic-workers.md); worker failure preserves checked partial samples without inferring a boundary. A separate [recorded entry point](diagnostic-recordings.md) commits original context, target plans, sample prefixes, and terminal evidence, and detects interrupted owners without resuming work. Full-size success does not invent a reduction; changed, incomplete, stale, or unsupported evidence is refused. Fresh originals are required again before constructing a checkpoint. This is a hypothesis generator, not a verified performance problem, enabled candidate catalog, grant, or production execution path. Protected production storage, service lifecycle and account validation, complete profile guards, review/session integration, and independent confirmation remain unfinished.

Run `test.bat`, `build.bat`, and `package.bat` as appropriate. Inspect the complete staged diff and run `node scripts/scan-staged.mjs` before a meaningful validated milestone commit. Never commit secrets or private runtime data. Do not mark unfinished requirements complete because compilation or unit tests pass. Do not publish releases automatically.
