# Dedicated Windows service

The optional `EstrogenPingPatch` Windows service runs as `NT AUTHORITY\LocalService`, not as an administrator or LocalSystem. It provides status plus bounded MTU preview, approval-recording, and cancellation jobs. Network configuration remains read-only: it cannot apply settings, restore snapshots, run shell commands, open arbitrary files, or accept AI proposals. Approving a preview records temporary permission metadata only; every preview result reports `executionAvailable: false`. Installing it does not make the optimizer complete or authorize future setting changes.

The service library now includes native read-only interface capture reused by desktop backups. `epp-network-service.exe --mtu-inventory` prints native interface snapshots; `--inspect-mtu GUID ipv4` or `ipv6` reads a specific interface without installing a service or requiring elevation. These commands use fixed Windows APIs and fixed driver/OS registry fields, not caller-supplied registry paths. Their diagnostic output can contain adapter/device identifiers and should stay private. They expose no setter.

Microsoft documents `SetIpInterfaceEntry` as requiring administrative privileges. The current LocalService identity is therefore insufficient for that future setter. A privileged-service identity/design change, scoped authorization, durable native checkpoints, persistent-store semantics, and independent failure recovery must be validated together before enabling it. The development launcher and desktop must remain unelevated.

## Management

Build or launch the development checkout first. In **Safety & privacy**, install the optional service, refresh its actual status, start/stop it, or uninstall it. The root `install-service.bat` and `uninstall-service.bat` provide the same installation/removal workflow. The packaged installer includes these helpers and the service executable. A normal development launch never requests elevation or installs a system service automatically.

The checkout helper selects the most recently built debug/release service executable. A packaged helper always uses its adjacent bundled executable, keeping those resources together. Rebuild before installation after changing service source.

Management alone requests Windows administrator approval. The original user's SID is captured before elevation and preserved if different administrator credentials are supplied. The service binary is copied to `%ProgramFiles%\estrogen ping patch service`; both the directory and executable are created with Administrators ownership and explicit ACLs allowing replacement only by administrators or SYSTEM. Ownership is established atomically at object creation rather than corrected after copying. The copied hash is checked before registration. Existing service installations/configurations and reparse points are rejected rather than overwritten. Startup is automatic; the GUI and internet are not needed to start the service. Installation trusts the build explicitly approved by the user; signing and authenticated upgrade distribution remain pending.

Use **Uninstall service** before removing the desktop application. The current per-user desktop uninstaller does not remove the separate machine-wide service automatically. Service removal stops its exact registered process, deletes its SCM entry, and removes only the known binary and an empty installation directory. It preserves user backups, measurements, and the machine recovery journal. Upgrades currently require explicit uninstall/reinstall; in-place service upgrade and reboot recovery are not yet validated.

## Recovery journal storage

Installation enables a service-specific SID and creates `%ProgramData%\estrogen-ping-patch-service` atomically with Administrators ownership and a protected DACL. SYSTEM and Administrators have full access; only `NT SERVICE\EstrogenPingPatch` receives data modification rights. Shared LocalService and interactive users receive no data access. An inheritable OWNER RIGHTS rule grants only READ_CONTROL, suppressing the implicit WRITE_DAC normally available to the shared account that owns newly created SQLite files.

The service resolves the machine data directory through Windows known folders rather than a caller-controlled data-path environment variable. Startup requires the service SID in its token, checks exact directory/file ACLs and owners, rejects reparse points and multiply linked files, and keeps directory handles open without delete sharing. It then opens and validates the local SQLite journal before reporting Running. Invalid permissions, unsupported schemas, missing original records, broken hashes, orphaned events, or corrupted storage prevent startup; existing evidence is preserved. A supported journal with unresolved work starts in read-only `recoveryRequired` mode. There is no native restore implementation to run yet.

The unelevated management path does not inspect private recovery files. Install/start checks those paths only after the separate administrator approval. Stop/uninstall can still remove the registered service when its journal is damaged; they never delete recovery data.

Status reports the journal verification time and unresolved checkpoint count as observed at service startup. The count includes both unfinished setting recovery and restored version-four checkpoints whose final policy verification is missing or unsuccessful. Each checkpoint is counted once; incomplete verification keeps status at `recoveryRequired`, even when its MTU restoration is complete. No operation can create or advance a checkpoint through IPC in this build. Service removal preserves the directory, and reinstallation reuses it only if its permissions match the expected policy. The journal is separate from user-owned diagnostic snapshots. See [checkpoint guarantees and remaining recovery gates](backups.md#service-checkpoint-journal).

The journal database is now schema four, retaining validated legacy checkpoints, native originals/readbacks, and [durable setting-process identities](mutators.md), and adding [policy-verification receipts](backups.md#durable-policy-verification-receipts). Its version is reported separately from pipe protocol schema four. Older service binaries cannot open the upgraded journal; reinstall a current service build after upgrading the desktop. The recovery coordinator library and disabled native lab handle pending policy verification, but the normal service is not wired to native setters or recovery commands. The existing Safety & privacy count includes pending final verification; separate per-checkpoint details remain unfinished. The normal LocalService reports `rollbackAvailable: false`; the separate recovery-only mode below reports its restoration capability.

The feature-gated [native MTU lab](native-mtu-lab.md) has a separately named service, storage directory, and LocalSystem account for an owned-loopback verification matrix. It is excluded from normal builds and installation. It does not change this service's account or network-read-only contract.

## Protocol and identity

- A fixed local pipe uses a protected DACL for SYSTEM, the service-specific SID, and the selected user's SID. User rights permit data exchange, attribute reads, and synchronization, without create-pipe-instance or security-descriptor modification rights.
- Remote clients are rejected, and the first server instance refuses an existing pipe name. Fresh instances preserve the namespace between clients; handles are not recycled after disconnect because the resolved Mio version retains stale completion state.
- The server reads the client's Windows token through identification-level pipe impersonation, compares the token user SID, and reverts before any asynchronous work. Failed reversion terminates the process. A successful ACL check alone does not dispatch a request.
- The client checks the kernel-reported pipe server PID against the running SCM service, requires session zero, verifies the registered process type/account, and rechecks the SCM PID after the response. An unregistered process imitating the pipe is rejected before receiving a request.
- Frames use a four-byte big-endian length followed by bounded UTF-8 JSON. The maximum payload is 4096 bytes. Schema, request identifier, operation, unknown fields, and a maximum five-second expiry are validated. Connection handling is bounded to five seconds, and a stop request cancels pending connection/frame work.

The contract now uses protocol schema four and pipe `estrogen-ping-patch-service-v4`. Replies bind schema, request identifier, and service PID to a typed result. It refuses earlier peers; uninstall/reinstall an older preview service to update its binary. Status includes a nullable recovery report. Only the paired read-only/LocalService and recovery-only/LocalSystem registrations are accepted; neither mode grants candidate modification permission.

`startMtuPreview`, `getMtuPreview`, `approveMtuPreview`, and `cancelMtuPreview` use the same authenticated boundary as status. Only GUID, family, proposed MTU, bounded lease, job/preview identifiers, and checkpoint hash are accepted. The service supplies the actual caller SID and captures the complete original itself. One worker handles capture and private grant storage outside the pipe loop; rejected scope, pending recovery, unavailable policy, or storage failure cannot enable settings changes. See [preview behavior and current limits](consent.md).

Read-only pipe access is not mutation authorization. Future writes need typed adapter-bound operations, expiring/revocable grants, exact service-owned checkpoints, independent recovery, and the backup gates in [backups](backups.md). No generic command, registry, executable, or endpoint escape hatch may be added.

## Recovery-only service mode

The optional `native-recovery` Cargo feature builds a separate service into `target/native-recovery` for installed recovery validation. `scripts/manage-service.ps1 -action install -recoveryOnly` selects only that isolated release binary and verifies its reported capability before installation. Normal desktop, build, package, and service installation workflows do not select this feature. Existing installations must be removed before changing modes; their protected journal is preserved. No recovery installation was performed on the development machine.

This mode uses the same fixed service name, protected installation/data directories, authenticated pipe, and authorized user. Its account is explicitly LocalSystem because LocalService cannot restore active interface MTU. Startup verifies session zero, service SID membership, SCM process type/PID/account, and the exact registered executable, mode, and owner command. Running the executable interactively cannot obtain recovery authority. The unelevated client requires the matching account/mode and rechecks the SCM registration and PID after exchange.

One background worker owns the protected journal and freezes its exact pending documents. Each operation receives its own bound original, so recovery can cover multiple adapters or address families without accepting a caller-supplied checkpoint or target. Preparation, candidate application, and retention are refused. The native writer uses only the exact original MTU; live GUID/LUID/name, OS/driver context, tracked-process exit, durable intent, native readback, and final policy checks remain mandatory. Apply grants, authorization storage, expired leases, service-stop state, the desktop, and network access cannot gate an original-value write already admitted for recovery.

Status distinguishes `running`, `completed`, and `recoveryRequired`, reports the final attention count and verified result count, and never claims apply permission. Failures preserve the journal and remain explicit. Restart retries pending recovery; completed records are excluded. Service stop lets an admitted restoration finish and stops before taking another record, publishing SCM stop progress while waiting. A native API that does not return remains a platform limitation; a progress report cannot make such a call preemptible.

`scripts/service-recovery-smoke.ps1 -allowNetworkChanges` refuses development and self-hosted execution before setup. On a fresh disposable hosted runner it creates one owned Microsoft loopback adapter and exercises IPv4 then IPv6, preserving the journal's one-pending-checkpoint barrier. An ignored helper uses fresh installed-reader policy captures and the fixed typed writer to stage MTU 1372, durably registering the actual suspended command before resume. The installed recovery service starts after each lease expires. The test requires exact MTU 1500 recovery, unchanged native/registry/active/persistent policy for both families, actual apply/restore process records, matched policy receipts, no authorization database, and no completed-checkpoint replay after restart. It separately checks empty startup and automatic SCM crash restart. The [hosted run at `3bf84b3`](https://github.com/celakk1/estrogen-ping-patch/actions/runs/41532334124) passed all of these checks. This establishes owned-adapter recovery in that Windows Server fixture; production candidate application, physical/client-OS/reboot recovery, and performance benefit remain unverified.

## Verification

Local tests exercise real Windows pipes, explicit ACL denial and minimal client permissions, independent token rejection, server PID mismatch, malformed/oversized frames, repeated connections, timeout recovery, service-stop cancellation, recovery ACL validation, and actual hard-link rejection. `scripts/service-smoke.ps1 -allowServiceInstallation` is reserved for an already elevated disposable Windows lab; CI runs it on the hosted runner. The original install/status/stop/restart/removal check passed. The extended check additionally verifies journal permissions, inserts a prepared simulated checkpoint through a test-only harness while stopped, confirms it is reported after startup, cancels that unapplied fixture, injects database corruption to require startup refusal, and verifies preservation across uninstall/reinstall. These extended checks passed at `1434e8a`: [service verification](https://github.com/celakk1/estrogen-ping-patch/actions/runs/41210675289). They never apply or restore a network setting. The developer's machine is not used for service installation testing.
