# MTU trial consent

The service library includes `MtuConsent`, a preview-and-approval controller for temporary MTU trials. The normal installed service now exposes authenticated preview, approval-recording, status, and cancellation operations through the version-four pipe. These operations can write private permission records, but cannot change Windows network settings. Desktop command bindings are present; the review screen and autonomous session workflow remain unfinished.

## Reviewed scope

A preview contains a random identifier, the exact version-four checkpoint hash, adapter GUID and OS/driver context, address family, original/proposed MTU, preview expiry, and trial expiry. Preview lifetime is at most thirty seconds and cannot exceed the trial lease. Retention permission is always false; keeping a setting requires a separate future approval flow.

Only one preview can await approval in a controller. It owns the original checkpoint; editing the returned preview cannot change that original. Approval requires the matching preview identifier and checkpoint hash from the same Windows owner. Cancelling, expiry, clock rollback, or a new controller instance makes the old identifier unusable. A monotonic deadline and the highest observed wall-clock time prevent old approval from being revived by a clock change, including after a rejected attempt to replace a pending preview.

The owner and actor SIDs are trusted service inputs, not identity evidence supplied in request JSON. The pipe handler supplies the actual Windows token SID after authenticating the caller. Request bodies accept no actor/owner SID, original snapshot, command, registry path, or endpoint. The native lab separately uses its already validated SCM owner; that fixture does not establish human consent.

## Grant and recovery boundaries

Creating a preview issues no grant. A valid approval consumes the pending preview before recording an exact, non-retaining grant through the protected authorization store. If recording fails, the same approval cannot be retried; another explicit preview and approval are required. The authorization store's unique checkpoint binding prevents silently issuing another grant when a previous commit actually succeeded.

A preview is not a durable backup. A recorded grant is permission, not proof of a setting change or successful restoration. The existing coordinator must still persist and verify the exact original and apply intent before any write, check live authorization, track the command process, and verify readback and recovery. Restoration remains independent of the approval controller and expired or revoked apply grants.

## Integration and limits

The owned-loopback lab obtains grants through preview and approval for both single and repeated trials. It immediately approves its own fixed fixture scope after SCM and target admission. The normal service instead captures a requested GUID/family itself, verifies complete native policy evidence, and waits for a matching authenticated approval request. Approval is consumed before opening grant storage; failed initialization cannot leave a reusable approval. Older grant storage remains readable; new previews admit only version-four policy-bound checkpoints.

The worker runs one job with one queued command and releases its state lock during provider/storage work. Status and cancellation remain responsive during capture. Cancelling approval either prevents grant creation or durably revokes a grant that committed while cancellation arrived. A failed revocation stays failed with its grant evidence retained. New work is refused until the current preview/approval is cancelled; unfinished recovery also blocks capture and grant issuance. The original backup is not committed by this preview path.

The CLI developer interface is `--preview-mtu GUID ipv4|ipv6 MTU LEASE_MS`, `--preview-status JOB_ID`, `--approve-mtu-preview JOB_ID PREVIEW_ID SHA256`, and `--cancel-mtu-preview JOB_ID`. Every result reports `executionAvailable: false`. Leases are bounded to 5..300 seconds and proposed MTUs to 1280..65535, strictly below the captured original. These are proposal inputs, not recommendations or enabled candidates. No setter, arbitrary command, registry path, executable, endpoint, or auto-approval path is exposed.

Tests cover exact scope and returned-data tampering, user/identifier/hash mismatch, cancellation, wall/monotonic expiry, clock rollback, restart, failed grant commits, storage initialization delay, single-use approval, and trial-lease bounds. Real-pipe tests use the actual Windows caller with simulated capture/storage fixtures. Installed-service positive capture and grant storage passed the hosted checks described below. Desktop review, session-wide consent, deterministic candidate admission, privileged execution, retention approval, and physical-adapter recovery still require implementation or validation.

This per-checkpoint controller does not replace session-wide consent. The autonomous application still needs approval of a bounded experiment plan so it can issue permitted trial grants without asking the user to approve every measurement or repeated bracket. Keeping a winning setting requires separate retention permission. The operation-level preview must not be presented as a finished autonomous optimizer.

## Session audit storage

The first delegated trial now atomically records the complete reviewed session scope and its grant-to-session link in [authorization database version two](authorization.md#durable-session-audit). Later grants share that exact scope and consume a persisted trial allowance. Failed scope/link writes leave neither a partial approval nor a grant, and end further delegation. Reopening preserves audit evidence while invalidating runtime authority; the existing approval cannot issue another grant from a fresh store instance. Session approval remains an internal library capability pending normal-service and desktop integration.

## Bounded repeated-session approval

The `automatic-trials` service library now includes `SessionConsent`. Its preview binds the exact policy-backed original and candidate, complete repeated-trial plan, configuration/environment/cohort hashes, metric rules, provider costs and traffic limits, block count, session deadline, and maximum individual trial lease. Trusted collector costs must fit the declared allowances, and aggregate/provider limits must cover every planned original/candidate/original bracket. The scope hash includes the random preview identity and the complete plan. A modified returned preview cannot expand the internally owned scope.

One matching approval consumes the preview and returns a non-cloneable in-memory session capability. It can issue at most the approved number of distinct checkpoint grants for the same owner, original configuration/policy, candidate, and unchanged plan. Fresh trial originals are still required; each lease stays within the approved maximum and session deadline. Reused checkpoint identifiers, longer leases, changed settings/policy/context, plan edits, and another owner are refused. Retention is always false. The existing host, coordinator, durable backup, watchdog, and collector checks remain mandatory before any setting write or traffic.

Session expiry uses both the original monotonic deadline and a wall-clock high-water mark. Failed grant storage ends further delegation and consumes the attempted checkpoint allowance. Cancellation stops issuance before attempting durable revocation of every known issued grant; failure on one does not prevent attempts on the others, and cancellation can be retried. Expiry while storage commits also stops delegation and attempts compensating revocation. Cancellation/expiry does not replace the independent watchdog's restoration duties.

The repeated native fixture uses one automatic fixture approval for its twelve trials and revokes every issued grant before reporting completion. Its hosted harness requires exactly one session-approval event, and independently inspects each persisted grant's scope, checksum, event chain, and terminal revocation. This fixture approval is not human consent. The normal installed service still exposes only operation-level read-only previews: session IPC, desktop review, production candidate admission, and privileged execution integration remain unfinished. A service restart discards the session capability; old permission records cannot reconstruct it or resume an experiment automatically.

The service workflow additionally runs `scripts/service-preview-smoke.ps1` on its own fresh hosted Windows runner. This harness creates and removes only its owned Microsoft loopback adapter, installs the ordinary LocalService binary, and checks positive preview, exact approval, durable grant revocation, and restart invalidation for both address families. It compares native context, registry origins, and active/persistent policy before and after approval and revocation. No MTU setter is called. The harness refuses development-machine execution, pre-existing service/storage, or a pre-existing Microsoft loopback device. The [hosted run at `d89493e`](https://github.com/celakk1/estrogen-ping-patch/actions/runs/41474261146) passed both the positive preview job and the separate service lifecycle job. This does not validate production setting changes or physical-adapter recovery.
