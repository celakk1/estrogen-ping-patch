# Native MTU recovery lab

The `native-mtu-lab` Cargo feature adds a separate, narrowly scoped Windows service for testing real Windows MTU writes and recovery. Default development, build, and packaging commands do not enable it. The normal LocalService service and desktop still expose no setters and report `rollbackAvailable: false`.

The lab is not an optimization feature or a production authorization mechanism. Its purpose is to establish native MTU behavior before enabling application-owned experiments. The current twenty-trial native matrix passed on a disposable Windows Server 2022 runner. This establishes the bounded loopback cases below, not production readiness or physical-adapter recovery.

## Isolation and authority

`scripts/native-mtu-lab.ps1 -allowNetworkChanges` is reserved for an elevated GitHub-hosted disposable Windows runner. It refuses ordinary development-machine execution before any device operation. Environment checks prevent accidental execution; they are not a security boundary against an administrator.

The harness creates one Microsoft loopback adapter through SetupAPI and the built-in `netloop.inf`, retaining its exact PnP instance ID and GUID. It assigns a unique `epp-mtu-lab-GUID` alias to its owned adapter before capturing the original. Existing loopback hardware, lab installations, and recovery storage cause refusal. It does not assign an IP address, change DNS, attach to a physical adapter, or create a default route. Cleanup removes only the device created by that process and the known lab executable; the recovery journal is retained.

The separately named `EstrogenPingPatchMtuLab` service runs as LocalSystem with an explicit service SID and a required-privilege list containing only `SeChangeNotifyPrivilege`. Its binary is copied and hash-verified in a protected Program Files directory. Its separate ProgramData journal uses the existing service-owned storage ACL and integrity checks. The production LocalService account is unchanged.

The lab entry point accepts only canonical owner SID, adapter GUID, family, interruption phase, and trial ID. It must enter through SCM, match the registered own-process LocalSystem PID in session zero, and possess the lab service SID. The mutation permit has no public constructor. Native target checks require the configured GUID/family, captured Microsoft loopback driver identity, root-enumerated network device, and Ethernet interface type. There is no mutation pipe, arbitrary executable, script, registry path, endpoint, or generic setter argument. The only candidate is MTU 1400; restoration permits the exact original value. Retention is always refused.

## Write and recovery path

The coordinator commits and reads back the native original and apply intent before calling the backend. Immediately before the write, the backend reacquires the GUID/LUID mapping and current IP row and checks the captured context, fixed alias, and every expected setting. It invokes only the protected system directory's `netsh.exe`, with a generated fixed argument list for `interface ipv4|ipv6 set subinterface`, the GUID-derived lab alias, the allowed MTU, and `store=active`. No executable, command text, policy store, script, or target name is accepted from a caller. The process has no terminal or input and a five-second deadline. Apply revocation and lease expiry terminate and reap its exact child; recovery remains independent of apply authorization. Command success is not readback evidence: the coordinator still requires the exact effective MTU and unchanged unrelated fields.

The whole-row `SetIpInterfaceEntry` approach failed the preservation gate on the disposable runner. Windows returned IPv4 `SitePrefixLength` 64, while the [setter requires zero on input](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-setipinterfaceentry). Passing zero changed that unrelated field. The lab therefore uses the [documented MTU-only subinterface operation](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-interface) instead of weakening comparisons or pretending zero restores the captured value. The complete matrix passed with this narrower operation.

Each trial has a 120-second wall-clock lease and monotonic deadline. Stopping the lab service releases an intentional pause and permits restoration. Startup processes its matching unresolved trial before considering new work, with recovery independent of an expired apply lease. A terminal trial ID cannot be replayed to apply a candidate again. Phase markers in the Application event log indicate that the native call returned; they do not themselves prove readback or durable completion. Only the verified journal and fresh observations establish the final result.

New trials require a [durable operation grant](authorization.md) before checkpoint preparation and application. Admission and the running command check the same exact scope. Restart recovery skips opening the separate grant database. The expanded matrix adds `revoke` and `authorization-unavailable` phases: revoke commits the grant's terminal event before the forced crash; the unavailable case temporarily replaces the closed grant database path with an empty directory while preserving its file and sidecars. Both restored through the intact recovery journal in the ten-trial run.

The command-lifetime revision uses an anonymous Windows job with kill-on-close, [assigned atomically through the process attribute list](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). The child starts suspended, and permission/deadline checks precede its resume. An explicit inherited-handle list contains only null input/output; the job handle cannot be retained by the child. Neither breakaway option is enabled, so ordinary descendants remain in the job. [Windows closes the job and terminates its processes when the last job handle closes](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), including on service-process death. Handled exits explicitly terminate the job and verify zero active processes before allowing coordinator readback or another write. If that verification fails, the instance blocks both new writes and recovery observations rather than finalizing a checkpoint from a potentially transient value. The command-lifetime revision passed the local process tests and the final ten-trial native run recorded below.

The Windows operation provides no compare-and-set transaction with the GUID validation. The unique lab alias avoids targeting a recycled numeric interface index, but checking immediately before a write and comparing afterward cannot eliminate races with an administrator renaming or replacing devices. Production policy/concurrency guards remain necessary.

[Process termination is asynchronous](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess) and pending I/O must finish or cancel before the process exits. Handled command cleanup therefore requires its process handle to signal, in addition to zero active job processes. The current revision adds a [durable pre-resume identity and restart exit barrier](mutators.md), with one active command process per job. Native target validation runs again after the process record commits and before resume. Restart verifies the exact creation time and process exit before reading or restoring settings; it never terminates a process by a saved PID. This revision's twelve-trial native crash matrix passed as recorded below; production watchdog and in-flight native-operation recovery remain unverified.

## Repeated native lifecycle fixture

The new `repeated` phase connects the durable experiment runner and service MTU host to the native lab backend. It plans twelve original/candidate/original blocks, with a fresh protected grant and tracked checkpoint for each temporary MTU 1400 trial, thirty-second candidate leases, and a five-minute overall limit. Each block must verify restoration before its final original baseline. Deterministic, domain-separated child UUIDs let startup recognize only this parent's twelve checkpoints; they do not grant write authority. Interrupted checkpoints are restored before experiment storage opens. Existing experiments are never replayed automatically.

Fixed `experiments.sqlite3` and `measurements.sqlite3` files live beside the protected lab recovery journal. Existing ownership, ACL, reparse-point, hard-link, and parent-directory guards apply to the databases and SQLite sidecars before and after initialization. Raw TCP baselines and checksum-linked native before/after receipts commit and read back before a metric session can be accepted. The experiment store remains schema one; measurement storage uses application schema six with a lab-owned receipt table carrying schema-one payloads. No public service protocol changes are introduced.

The fixture uses software-loopback IPv4 and IPv6 TCP listeners, saves thirty-six six-probe raw sessions, and requires 216 accepted connections plus twelve restored native checkpoints and twenty-four tracked setting commands. The listeners' routes do not traverse the separate owned Microsoft adapter whose MTU is changed. This verifies native write/measurement/restore coordination and evidence binding, not the performance effect of that MTU. Receipts explicitly label the software-loopback lifecycle scope; the fixture's deliberately large improvement threshold must leave its comparison exploratory and inconclusive.

The PowerShell harness adds one repeated run per family. A separate Node.js verifier reads stable copies of the stopped service's databases, checks source bytes remain unchanged, verifies checksums, raw-derived medians, cohort/environment/configuration bindings, native MTU readbacks, recovery chains, and command records. It uses the bundled [Node 24 read-only SQLite API](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html); it never opens the original service databases through SQLite.

The first hosted attempt stopped at plan validation before a repeated candidate could be prepared: the fixture accidentally applied its 1000 ms latency threshold to percentage metrics. A constructor regression test reproduced that exact refusal; percentage improvement now matches the 0.1 percentage-point resolution, with zero permitted failure regression/drift. The corrected feature suite passes 106 tests with ten explicit subprocess helpers ignored, plus feature Clippy. The independent route-fingerprint reconstruction also matched actual Windows baseline exports locally.

At `5b1e881`, the [hosted repeated-native run](https://github.com/celakk1/estrogen-ping-patch/actions/runs/41332938909) passed thirteen core experiment tests, 106 feature tests, Clippy, the isolated release build, and all twenty-two cases. Independent log inspection verified eleven cases per family, exact original/final MTU 1500, and expected write/process counts. Each repeated case completed twelve blocks, thirty-six raw sessions, 216 successful connections, twelve restored checkpoints, and twenty-four tracked setting commands. Across both families this adds twenty-four temporary trials and seventy-two raw sessions. No setting was retained. Affected-path performance, physical/client-OS support, reboot recovery, and installed-service integration remain unverified.
